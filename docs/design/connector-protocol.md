# Connector protocol — design note

**Date:** 2026-05-07  
**Status:** draft  
**Implements:** [ADR-0011](../adr/ADR-0011-connector-isolation.md) (with applicable amendments from this note)  
**Related:** [Connector SDK](../02_CONNECTOR_SDK.md) · [Architecture §9](../01_ARCHITECTURE.md#9-connector-framework--the-most-important-dx-surface)

---

## Goals

- Define a **newline-delimited JSON protocol over stdin/stdout** that supports the operations exposed by the SDK's `ConnectorContext`.
- Make protocol compatibility **versioned and negotiated once per connector spawn**, so runtimes can support older connectors within an intentional major-version window.
- Keep protocol failures **diagnostic enough to debug a stuck or failing connector** without attaching a debugger to either process.
- Preserve the SDK promise that connector authors write against **one `ConnectorContext` shape** while dev and production swap transport implementations.
- Keep the message set small enough that a hand-written non-Python connector remains plausible if ADR-0011's open question later becomes product scope.

## Non-goals

- **Not** a general-purpose IPC framework. This protocol exists for connector-runtime communication, not arbitrary process coordination.
- **Not** a streaming framework. Bulk emission is supported, but this is not Kafka, NATS, or a sustained high-throughput transport. Connectors that need those systems should write to them directly, with prow orchestrating.
- **Not** the supervisor design. Spawn, restart, crash detection, grace periods, and watchdog policy belong to the runtime design note. This note specifies the wire shape.
- **Not** the connector author's API. Authors call `ctx.emit()`, `ctx.set_state()`, `ctx.log`, and `ctx.metrics`; the protocol is the framework's implementation detail.

## Framing and encoding

**Framing:** each protocol message is one newline-terminated JSON document. Embedded newlines inside field values are escaped by JSON string rules. Empty lines are malformed messages.

**Encoding:** UTF-8, with no byte-order mark. Invalid UTF-8 is rejected as `malformed-message` with details identifying the read side and byte offset where available. The runtime treats decode as fallible input handling, not as an exceptional crash path.

**Direction:** the runtime writes protocol messages to connector stdin; the connector writes protocol messages to stdout. Connector stderr is reserved for unstructured human-readable output: Python tracebacks, dependency warnings, and accidental library noise. The runtime captures stderr for operator diagnostics but never parses it as protocol.

**Line length:** v1 has a soft limit of 1 MiB per JSON line after UTF-8 encoding. Larger logical emits are split by the framework into multiple `emit` messages. The connector author emits a bundle; the SDK transport owns chunking decisions.

**Buffering:** both sides flush after every message. A connector that buffers stdout will look hung. The SDK-provided transport performs flushing; connector authors do not call `flush()` directly.

## Message schema

Every message uses the same envelope:

```json
{"v":1,"id":"01H...","kind":"emit","payload":{"type":"bundle","objects":[]}}
```

- `v` is the negotiated protocol version, an integer constant for the lifetime of the spawn.
- `id` is a ULID or UUID generated by the sender. It correlates requests, acks, and diagnostics.
- `kind` is the lowercase message type. Multi-word kinds are hyphenated.
- `payload` is kind-specific JSON content.

Response messages use the same envelope and may add:

- `id_ref`, the `id` of the message being answered.
- `error`, present only on failure, with `code`, `message`, and optional `details`.

Unless stated otherwise, failures are returned using the expected response kind with `error` populated. Unknown or unparseable messages are answered with `malformed-message` or `unknown-kind` only when the receiver can still safely write a response.

## Message kinds

### Lifecycle

**`hello`** starts the session and is always the first runtime to connector message. Payload fields: `runtime_version` string, `supported_protocol_versions` array of integers, `connector_id` string, `instance_id` string, and `config` object. Direction: runtime to connector. Response: `hello-ack`. Failure modes: malformed config or absent compatible protocol version yields `unsupported-version`; invalid payload shape yields `malformed-message`. The `config` object may contain secrets and must not be logged raw by the runtime.

**`hello-ack`** confirms the connector can speak one advertised version. Payload fields: `protocol_version` integer, `connector_sdk_version` string optional, `connector_package` string optional, and `capabilities` object optional. Direction: connector to runtime. It responds to `hello` via `id_ref`. Failure modes: if `protocol_version` is not supported by the runtime, the runtime reports `unsupported-version` and closes the connection. No other protocol messages are valid before this exchange completes.

**`shutdown`** requests graceful termination. Payload fields: `reason` string optional and `deadline_ms` integer optional, provided for diagnostics; authoritative timeout policy lives in the runtime design. Direction: runtime to connector. Response: `shutdown-ack`. Failure modes: malformed payload gets `malformed-message`; failure to answer is handled by the supervisor, not by an error message.

**`shutdown-ack`** confirms graceful shutdown. Payload fields: `status` string, one of `ok` or `busy`, and `message` string optional. Direction: connector to runtime. It responds to `shutdown`; the connector exits after flushing it. Failure modes are limited because this is normally the last message.

### Operational — connector-initiated

**`emit`** carries one STIX 2.1 bundle for validation, deduplication, and persistence. Payload is the bundle as a STIX dict: required `type: "bundle"`, required `id`, required `objects` array, plus standard STIX bundle fields if present. Direction: connector to runtime. Response: `emit-ack`; `ctx.emit()` resolves only after it arrives. Failure modes: invalid JSON shape is `malformed-message`; STIX failures are `validation-error`; oversized messages are `malformed-message` with `details.limit_bytes`.

**`emit-ack`** reports ingest outcome. Payload fields: `accepted_count` integer, `duplicate_count` integer, `failed_count` integer, `accepted_object_ids` array optional, `duplicate_object_ids` array optional, and `validation_failures` array optional. Direction: runtime to connector. It responds to `emit`. Partial validation failure is represented in the payload when the bundle itself was received and processed; a whole-message failure uses `error`.

**`log`** forwards one structured log record. Payload fields: `level` string, `message` string, `timestamp` string in ISO 8601 UTC, `fields` object optional, and `exception` object optional with `type`, `message`, and `stack` strings where available. Direction: connector to runtime. No ack; fire-and-forget. Failure modes: malformed records may be dropped and counted by the runtime, but the runtime should not answer because log delivery must not deadlock connector work.

**`metric`** forwards one metric observation. Payload fields: `name` string, `kind` string (`counter`, `gauge`, or `histogram`), `value` number, `timestamp` string optional, `unit` string optional, and `tags` object optional. Direction: connector to runtime. No ack. Failure modes: malformed metric records may be dropped with runtime-side diagnostics; no protocol error is returned.

**`set-state`** writes connector-owned persistent state. Payload fields: `key` string and `value` JSON value; optional `compare_version` string supports later optimistic writes but is nullable in v1. Direction: connector to runtime. Response: `set-state-ack`. Failure modes: invalid key shape is `malformed-message`; key over budget is `state-key-too-large`; value over budget is `state-value-too-large`; storage failure is `internal-error`.

**`set-state-ack`** confirms a state write. Payload fields: `key` string, `version` string optional, and `written` boolean. Direction: runtime to connector. It responds to `set-state`. Failure responses use the error codes above.

**`get-state`** reads connector-owned persistent state. Payload fields: `key` string and `default` JSON value optional. Direction: connector to runtime. Response: `get-state-ack`. Failure modes: invalid key shape is `malformed-message`; oversized key is `state-key-too-large`; storage failure is `internal-error`.

**`get-state-ack`** returns state. Payload fields: `key` string, `found` boolean, `value` JSON value, and `version` string optional. Direction: runtime to connector. It responds to `get-state`. If not found, `found` is false and `value` is the supplied default or null.

### Operational — runtime-initiated

**`health`** probes connector liveness and self-reported status. Payload fields: `scope` string optional (`process`, `connector`, or `operation`) and `deadline_ms` integer optional for diagnostics. Direction: runtime to connector. Response: `health-ack`. Failure modes: malformed payload is `malformed-message`; missing response is a supervisor observation.

**`health-ack`** reports health. Payload fields: `status` string (`ok`, `degraded`, or `unhealthy`), `message` string optional, and `details` object optional. Direction: connector to runtime. It responds to `health`. Errors are reserved for malformed requests or connector-internal exceptions while computing health.

**`cancel`** requests cooperative cancellation of current work, for example a `fetch()` call running too long. Payload fields: `reason` string optional and `operation_id` string optional. Direction: runtime to connector. No ack in v1; cancellation is observed through the operation ending, a later `health-ack`, or process termination. Failure modes are intentionally sparse: if the connector cannot process messages, the supervisor escalates.

## Versioning and negotiation

Protocol negotiation happens once per spawn. The runtime sends `hello` with all versions it can speak. The connector answers `hello-ack` with exactly one version. Every later message carries that value in `v`; a different value is `malformed-message`.

Protocol versions follow integer semver-major semantics. A v1 runtime can speak to a v1 connector. A v2 runtime may support v1 connectors during a deprecation window, but it is not required by this protocol note; the runtime design note sets the policy and operator controls.

If the connector chooses a version the runtime cannot speak, the runtime closes the connection and reports an actionable error: supported versions, advertised version, connector package if known, and upgrade guidance. Version 1 is the complete scope of this note. Future protocol versions amend this document append-only for compatible clarifications and use a new design note for substantial revisions.

## Error model

Errors live in the `error` field on response envelopes. The starting `code` enum is: `unsupported-version`, `malformed-message`, `unknown-kind`, `validation-error`, `state-key-too-large`, `state-value-too-large`, and `internal-error`.

`message` is human-readable: stable enough to grep logs, not stable enough to parse. `details` carries kind-specific structured data. For `validation-error`, `details` includes per-object failures from `prow.stix._validate.StixValidationError`, including object ID when known, STIX type when known, path, and validator message. The principle is diagnostics first and programmatic handling second. A connector author reading the error in logs should know whether to fix their bundle, shrink state, upgrade SDK, or file a prow bug.

## Backpressure and ordering

`emit` is acknowledged, not fire-and-forget. `ctx.emit()` returns only after `emit-ack`, making the runtime's validator and persister the natural backpressure point. A slow persister stalls fast emitters automatically.

Ordering is preserved per direction: connector stdout is read in order, and runtime stdin writes are sent in order. The protocol does not define cross-direction ordering; a `cancel` may be interleaved with connector-originated `emit` messages.

A connector may keep multiple `emit`, `set-state`, and `get-state` calls in flight, each with a different `id`. The v1 maximum is 64 in-flight acknowledged operations per connector instance. At the limit, the SDK transport waits before sending another acknowledged operation. If a connector bypasses the SDK and exceeds the limit, the runtime may return `malformed-message` with `details.limit`.

## Security posture

The protocol runs over OS pipes between a runtime and a child process it spawned. The connector subprocess is trusted for protocol purposes: it is code installed from a Python package and runs with the permissions granted to Python. This is a plugin threat model, not a sandbox. The protocol does not defend against a malicious connector exfiltrating config, burning CPU, or intentionally emitting hostile but valid data; those concerns require packaging policy, sandboxing, and runtime supervision outside v1.

The protocol does defend against malformed input. Invalid UTF-8, invalid JSON, unknown kinds, oversized lines, and invalid STIX bundles must not crash the runtime. Every parse is fallible.

Connector configuration in `hello.payload.config` may contain secrets. Runtime logging redacts known-secret keys before recording `hello`. The protocol itself does not redact; redaction is a runtime concern.

## Open questions

- **Streaming emit for large bundles:** the 1 MiB line limit is fine for typical bundles, but URLhaus `recent` can exceed it. Should v2 add `emit-stream-begin` / `emit-chunk` / `emit-stream-end`, or should the SDK chunk into multiple normal `emit` messages? Lean: SDK chunks; implementation discovery should measure validation and dedup effects.
- **Bidirectional `cancel` ack:** v1 has no `cancel-ack`; the runtime observes cancellation by operation completion or process exit. A cheap explicit ack may be worth adding before acceptance so the runtime can distinguish "signal received" from "connector stopped reading." Lean: add it if the runtime note finds a real state transition for it.
- **Non-Python connectors:** the wire is language-agnostic, but the SDK is Python-only. A future bridge over gRPC, MessagePack, or another transport is plausible. Defer until demand exists; this v1 design does not preclude it.
- **State size budgets:** suggested limits are 1 MiB per state value and 16 MiB total state per connector instance. A connector storing all fetched IDs can otherwise fill memory or storage. The exact numbers need review with the persistence design.

## Conflicts with the existing SDK doc

`docs/02_CONNECTOR_SDK.md` predates ADR-0011 and this protocol. Its examples calling `await ctx.emit(...)` and reading `ctx.last_run_at` remain correct at the author API surface, but the SDK doc should explain that production `emit`, state reads, state writes, logs, and metrics become protocol messages under the hood.

The SDK doc still says connectors run as `asyncio` tasks in the monolith. ADR-0011 supersedes that for production monolith runs; only `prow connector dev` keeps the in-process fast path. The architecture doc has been updated, but the SDK doc still needs the same correction.

The `ConnectorContext` section lists fields and methods without naming the dev-vs-prod transport split. That split belongs primarily to the runtime design note, but the SDK doc should defer to it explicitly once both design notes are accepted.

Recommendation: amend the SDK doc in a separate follow-up PR after this protocol note and the runtime/supervisor note are accepted, so the public SDK language changes coherently rather than incrementally.
