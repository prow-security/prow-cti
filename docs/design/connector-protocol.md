# Connector protocol — design note

**Date:** 2026-05-07  
**Status:** draft  
**Implements:** [ADR-0011](../adr/ADR-0011-connector-isolation.md) (with applicable amendments from this note)  
**Related:** [Connector SDK](../02_CONNECTOR_SDK.md) · [Architecture §9](../01_ARCHITECTURE.md#9-connector-framework--the-most-important-dx-surface)

---

## Goals

- Define a **newline-delimited JSON protocol over stdin/stdout** that supports the operations exposed by the SDK's `ConnectorContext`.
- Make protocol compatibility **versioned and negotiated once per connector spawn**, so runtimes can support older connectors within an intentional major-version window.
- Keep protocol failures **diagnostic enough to debug a stuck or failing connector** without attaching a debugger to either process.
- Preserve the SDK promise that connector authors write against **one `ConnectorContext` shape** while dev and production swap transport implementations.
- Keep the message set small enough that a hand-written non-Python connector remains plausible if ADR-0011's open question later becomes product scope.

## Non-goals

- **Not** a general-purpose IPC framework. This protocol exists for connector-runtime communication, not arbitrary process coordination.
- **Not** a streaming framework. Bulk emission is supported, but this is not Kafka, NATS, or a sustained high-throughput transport. Connectors that need those systems should write to them directly, with prow orchestrating.
- **Not** the supervisor design. Spawn, restart, crash detection, grace periods, and watchdog policy belong to the runtime design note. This note specifies the wire shape.
- **Not** the connector author's API. Authors call `ctx.emit()`, `ctx.set_state()`, `ctx.log`, and `ctx.metrics`; the protocol is the framework's implementation detail.

## Framing and encoding

**Framing:** each protocol message is one newline-terminated JSON document. Embedded newlines inside field values are escaped by JSON string rules. Empty lines are malformed messages.

**Encoding:** UTF-8, with no byte-order mark. Invalid UTF-8 is rejected as `malformed-message` with details identifying the read side and byte offset where available. The runtime treats decode as fallible input handling, not as an exceptional crash path.

**Direction:** the runtime writes protocol messages to connector stdin; the connector writes protocol messages to stdout. Connector stderr is reserved for unstructured human-readable output: Python tracebacks, dependency warnings, and accidental library noise. The runtime captures stderr for operator diagnostics but never parses it as protocol.

**Line length:** v1 has a soft limit of 1 MiB per JSON line after UTF-8 encoding. Larger logical emits are split by the framework into multiple `emit` messages. The connector author emits a bundle; the SDK transport owns chunking decisions.

**Buffering:** both sides flush after every message. A connector that buffers stdout will look hung. The SDK-provided transport performs flushing; connector authors do not call `flush()` directly.

## Message schema

Every message uses the same envelope:

```json
{"v":1,"id":"01H...","kind":"emit","payload":{"type":"bundle","objects":[]}}
```

- `v` is the negotiated protocol version, an integer constant for the lifetime of the spawn.
- `id` is a ULID or UUID generated by the sender. It correlates requests, acks, and diagnostics.
- `kind` is the lowercase message type. Multi-word kinds are hyphenated.
- `payload` is kind-specific JSON content.

Response messages use the same envelope and may add:

- `id_ref`, the `id` of the message being answered.
- `error`, present only on failure, with `code`, `message`, and optional `details`.

Unless stated otherwise, failures are returned using the expected response kind with `error` populated. Unknown or unparseable messages are answered with `malformed-message` or `unknown-kind` only when the receiver can still safely write a response.

## Message kinds

### Lifecycle

**`hello`** starts the session and is always the first runtime to connector message. Payload fields: `runtime_version` string, `supported_protocol_versions` array of integers, and `config` object. (Connector identity and instance identity are passed in environment variables — `PROW_CONNECTOR_ENTRY_POINT` and `PROW_CONNECTOR_INSTANCE_ID` — so the connector-side logger can bind them before the first frame is written. See the runtime design note for the rationale.) Direction: runtime to connector. Response: `hello-ack`. Failure modes: malformed config or absent compatible protocol version yields `unsupported-version`; invalid payload shape yields `malformed-message`. The `config` object may contain secrets and must not be logged raw by the runtime.

**`hello-ack`** confirms the connector can speak one advertised version. Payload fields: `protocol_version` integer and `connector_version` string. (The earlier draft mentioned optional `connector_sdk_version`, `connector_package`, and `capabilities` fields; v1 ships with just the two required fields and `extra = "forbid"` on the payload model. Adding capability negotiation will require a protocol-version bump.) Direction: connector to runtime. It responds to `hello` via `id_ref`. Failure modes: if `protocol_version` is not supported by the runtime, the runtime reports `unsupported-version` and closes the connection. No other protocol messages are valid before this exchange completes.

**`shutdown`** requests graceful termination. Payload fields: `grace_period_seconds` integer, default 30. (The earlier draft mentioned optional `reason` and `deadline_ms` diagnostic fields; v1 ships with the single `grace_period_seconds` field and `extra = "forbid"`.) Direction: runtime to connector. Response: `shutdown-ack`. Failure modes: malformed payload gets `malformed-message`; failure to answer is handled by the supervisor, not by an error message.

**`shutdown-ack`** confirms graceful shutdown. Payload is empty. (The earlier draft listed a `status: ok|busy` field and an optional `message`; v1 ships with an empty payload because the connector is free to exit immediately after writing the ack.) Direction: connector to runtime. It responds to `shutdown`; the connector exits after flushing it. Failure modes are limited because this is normally the last message.

### Operational — connector-initiated

**`emit`** carries one STIX 2.1 bundle for validation, deduplication, and persistence. Payload field: `bundle` object — the bundle as a STIX dict, with required `type: "bundle"`, required `id`, required `objects` array, plus standard STIX bundle fields if present. (The earlier draft envisioned the payload itself being the bundle dict; v1 wraps it in a single `bundle` field so the envelope's `payload` slot stays consistent across kinds.) Direction: connector to runtime. Response: `emit-ack`; `ctx.emit()` resolves only after it arrives. Failure modes: invalid JSON shape is `malformed-message`; STIX failures are `validation-error`; oversized messages are `malformed-message` with `details.limit_bytes`.

**`emit-ack`** reports ingest outcome. Payload fields: `accepted` integer, `duplicates` integer, and `validation_failures` array of `{object_id, error}` objects. (The earlier draft used `accepted_count` / `duplicate_count` / `failed_count` plus optional `accepted_object_ids` / `duplicate_object_ids` arrays; v1 ships with the simpler trio because `failed_count` is `len(validation_failures)` and per-object id arrays were never consumed by the runtime. Field names changed; behaviour did not.) Direction: runtime to connector. It responds to `emit`. Partial validation failure is represented in the payload when the bundle itself was received and processed; a whole-message failure uses `error`.

**`log`** forwards one structured log record. Payload fields: `level` string, `message` string, `timestamp` string in ISO 8601 UTC, `fields` object, and `exception` string or null. (The earlier draft modelled `exception` as a structured `{type, message, stack}` object; v1 ships with `exception: str | None` carrying the full formatted traceback because the connector subprocess already has the traceback as a string and structured exception parsing on the runtime side has no current consumer. Adding the structured form back is a forward-compatible payload extension.) Direction: connector to runtime. No ack; fire-and-forget. Failure modes: malformed records may be dropped and counted by the runtime, but the runtime should not answer because log delivery must not deadlock connector work.

**`metric`** forwards one metric observation. Payload fields: `name` string, `value` number, `unit` string or null, `tags` object of string-to-string pairs, and `timestamp` string. (The earlier draft required a `kind` field with `counter`/`gauge`/`histogram` values; v1 ships without `kind` because the metric is forwarded as an OpenTelemetry observation and the receiving meter decides the instrument shape. Reintroducing `kind` is a forward-compatible payload extension when the runtime grows histogram support.) Direction: connector to runtime. No ack. Failure modes: malformed metric records may be dropped with runtime-side diagnostics; no protocol error is returned.

**`set-state`** writes connector-owned persistent state. Payload fields: `key` string and `value` JSON value. (The earlier draft mentioned an optional `compare_version` for optimistic writes; v1 ships without it and `extra = "forbid"`. Optimistic writes will need a protocol-version bump or a forward-compatible payload extension when the persister supports them.) Direction: connector to runtime. Response: `set-state-ack`. Failure modes: invalid key shape is `malformed-message`; key over budget is `state-key-too-large`; value over budget is `state-value-too-large`; storage failure is `internal-error`.

**`set-state-ack`** confirms a state write. Payload is empty. (The earlier draft listed `key`, optional `version`, and `written` fields; v1 ships with an empty payload because the runtime answers only on success and answers with the error envelope on failure.) Direction: runtime to connector. It responds to `set-state`. Failure responses use the error codes above.

**`get-state`** reads connector-owned persistent state. Payload field: `key` string. (The earlier draft mentioned an optional `default` field; v1 places the default-on-miss policy on the connector-side `ctx.get_state(key, default=...)` API rather than on the wire, so the protocol does not carry `default`.) Direction: connector to runtime. Response: `get-state-ack`. Failure modes: invalid key shape is `malformed-message`; oversized key is `state-key-too-large`; storage failure is `internal-error`.

**`get-state-ack`** returns state. Payload field: `value` JSON value or null. (The earlier draft listed `key`, `found`, `value`, and optional `version`; v1 ships with a single `value` field that is `null` on miss because the requesting `id_ref` already pairs the response with its request and `found` is `value is not None` once miss-distinguishing is needed.) Direction: runtime to connector. It responds to `get-state`.

### Operational — runtime-initiated

**`health`** probes connector liveness and self-reported status. Payload is empty. (The earlier draft mentioned optional `scope` and `deadline_ms` diagnostic fields; v1 ships with an empty payload and `extra = "forbid"`. Adding probe scope is a forward-compatible extension when scoped probes have a real consumer.) Direction: runtime to connector. Response: `health-ack`. Failure modes: malformed payload is `malformed-message`; missing response is a supervisor observation.

**`health-ack`** reports health. Payload fields: `status` string (`healthy`, `degraded`, or `unhealthy`) and `details` object. (The earlier draft used `ok` as the well status; v1 ships with `healthy` instead because `ok` was ambiguous with a `result-ok` semantic the protocol does not have. The optional `message` field was folded into `details`.) Direction: connector to runtime. It responds to `health`. Errors are reserved for malformed requests or connector-internal exceptions while computing health.

**`cancel`** requests cooperative cancellation of current work, for example a `fetch()` call running too long. Payload field: `target_id` string identifying the operation envelope to cancel. (The earlier draft mentioned optional `reason` and `operation_id` fields; v1 ships with the single required `target_id` and `extra = "forbid"`.) Direction: runtime to connector. Response: `cancel-ack`. (The earlier draft stated "No ack in v1; cancellation is observed through the operation ending." That was amended during Pass C2: an explicit ack lets the supervisor distinguish "signal received" from "connector stopped reading", which makes the cancellation state machine meaningful. The ack payload field is `cancelled: bool`.)

**`cancel-ack`** confirms a cancellation request was observed. Payload field: `cancelled` boolean — `true` when the connector-side runtime found a matching in-flight operation and signalled it, `false` when no such operation existed. Direction: connector to runtime. It responds to `cancel`. The ack means the cancellation was observed, not that user-level cleanup has finished.

## Versioning and negotiation

Protocol negotiation happens once per spawn. The runtime sends `hello` with all versions it can speak. The connector answers `hello-ack` with exactly one version. Every later message carries that value in `v`; a different value is `malformed-message`.

Protocol versions follow integer semver-major semantics. A v1 runtime can speak to a v1 connector. A v2 runtime may support v1 connectors during a deprecation window, but it is not required by this protocol note; the runtime design note sets the policy and operator controls.

If the connector chooses a version the runtime cannot speak, the runtime closes the connection and reports an actionable error: supported versions, advertised version, connector package if known, and upgrade guidance. Version 1 is the complete scope of this note. Future protocol versions amend this document append-only for compatible clarifications and use a new design note for substantial revisions.

## Error model

Errors live in the `error` field on response envelopes. The starting `code` enum is: `unsupported-version`, `malformed-message`, `unknown-kind`, `validation-error`, `state-key-too-large`, `state-value-too-large`, and `internal-error`.

`message` is human-readable: stable enough to grep logs, not stable enough to parse. `details` carries kind-specific structured data. For `validation-error`, `details` includes per-object failures from `prow.stix._validate.StixValidationError`, including object ID when known, STIX type when known, path, and validator message. The principle is diagnostics first and programmatic handling second. A connector author reading the error in logs should know whether to fix their bundle, shrink state, upgrade SDK, or file a prow bug.

## Backpressure and ordering

`emit` is acknowledged, not fire-and-forget. `ctx.emit()` returns only after `emit-ack`, making the runtime's validator and persister the natural backpressure point. A slow persister stalls fast emitters automatically.

Ordering is preserved per direction: connector stdout is read in order, and runtime stdin writes are sent in order. The protocol does not define cross-direction ordering; a `cancel` may be interleaved with connector-originated `emit` messages.

A connector may keep multiple `emit`, `set-state`, and `get-state` calls in flight, each with a different `id`. The v1 maximum is 64 in-flight acknowledged operations per connector instance. At the limit, the SDK transport waits before sending another acknowledged operation. If a connector bypasses the SDK and exceeds the limit, the runtime may return `malformed-message` with `details.limit`.

## Security posture

The protocol runs over OS pipes between a runtime and a child process it spawned. The connector subprocess is trusted for protocol purposes: it is code installed from a Python package and runs with the permissions granted to Python. This is a plugin threat model, not a sandbox. The protocol does not defend against a malicious connector exfiltrating config, burning CPU, or intentionally emitting hostile but valid data; those concerns require packaging policy, sandboxing, and runtime supervision outside v1.

The protocol does defend against malformed input. Invalid UTF-8, invalid JSON, unknown kinds, oversized lines, and invalid STIX bundles must not crash the runtime. Every parse is fallible.

Connector configuration in `hello.payload.config` may contain secrets. Runtime logging redacts known-secret keys before recording `hello`. The protocol itself does not redact; redaction is a runtime concern.

## Open questions

- **Streaming emit for large bundles:** the 1 MiB line limit is fine for typical bundles, but URLhaus `recent` can exceed it. Should v2 add `emit-stream-begin` / `emit-chunk` / `emit-stream-end`, or should the SDK chunk into multiple normal `emit` messages? Lean: SDK chunks; implementation discovery should measure validation and dedup effects.
- **Bidirectional `cancel` ack:** v1 has no `cancel-ack`; the runtime observes cancellation by operation completion or process exit. A cheap explicit ack may be worth adding before acceptance so the runtime can distinguish "signal received" from "connector stopped reading." Lean: add it if the runtime note finds a real state transition for it.
- **Non-Python connectors:** the wire is language-agnostic, but the SDK is Python-only. A future bridge over gRPC, MessagePack, or another transport is plausible. Defer until demand exists; this v1 design does not preclude it.
- **State size budgets:** suggested limits are 1 MiB per state value and 16 MiB total state per connector instance. A connector storing all fetched IDs can otherwise fill memory or storage. The exact numbers need review with the persistence design.

## Conflicts with the existing SDK doc

The Pass D stabilisation pass amended `docs/02_CONNECTOR_SDK.md` to align it with the shipped protocol:

- `await ctx.emit(...)` and `ctx.last_run_at` remain correct at the author API surface; the SDK doc now reflects the actual `ConnectorContext` field set.
- The SDK doc no longer asserts that production runs are in-process; subprocess isolation per ADR-0011 is documented as the production model, and the dev-vs-prod transport split is named explicitly.
- The deferred-vs-shipped split for `ctx.http()`, `ctx.files()`, `ctx.metrics`, and the test harness is now spelled out so connector authors know what to use today.
